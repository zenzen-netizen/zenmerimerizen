## FASE 0 — RECON (baca, lapor) ✅

### 1. computeDeployAmount (config.js:483-492) — gimana nentuin jumlah deploy?
```
deployable = max(0, walletSol − gasReserve)
dynamic    = deployable × positionSizePct
result     = clamp(dynamic, floor=deployAmountSol, ceil=maxDeployAmount)  → toFixed(2)
```
- **Skala saldo?** YA (compounding) — naik linear dgn wallet via positionSizePct.
- **Floor deployAmountSol?** YA — selalu di-clamp ke `≥ deployAmountSol`. (v2: floor 0.2.)
- **Jamin maxPositions semua kebuka?** ❌ **TIDAK.** Formula **buta jumlah-slot** — cuma fungsi(walletSol).
  Tiap deploy makan `positionSizePct` dari deployable; gak ada pembagian eksplisit ke N slot, gak cadangkan
  rent posisi lain. Posisi ke-2/3 dapat sisa acak; bisa ke-floor di deployAmountSol meski wallet tipis.
- **Caller (4):** index.js:731 (screening OTONOM — jalur utama; `prePositions` & `preBalance` ADA di scope →
  slotsRemaining bisa dihitung), index.js:1550 (display /wallet "Next deploy"), index.js:3220 (manual /deploy),
  tools/dlmm.js:725 (fallback kalau amount kosong, jarang). Screener DIBERITAHU angka di prompt (index.js:999
  `Deploy: ${deployAmount} SOL`) lalu pakai sbg `amount_y`.

### 2. Balance check pre-deploy (executor.js:1031-1038) — cadangkan rent?
```
minRequired = amountY + gasReserve          // ← rent TIDAK dicadangkan
if (balance.sol < minRequired) reject
```
- **KONFIRMASI AUDIT: BENAR — rent TIDAK dicadangkan.** Rent posisi (~0.057 SOL, dikunci di akun posisi,
  refundable saat close) keluar TAMBAHAN saat deploy. Karena check cuma jamin `amountY+gasReserve`, rent
  makan ke buffer gas / kalau mepet → **posisi ke-N gagal** (tx kurang SOL). + ada **minDeploy floor**
  (executor.js:1004): `minDeploy = max(0.1, deployAmountSol)` → kalau deployAmountSol 0.2, deploy <0.2 DITOLAK.

### 3. maxPositions di-enforce di mana? interaksi sizing × slot?
- **Enforce:** screening guard index.js:660 (`prePositions >= maxPositions` → skip cycle) + executor.js:966
  (deploy_position safety: `total_positions >= maxPositions` → reject, pakai `force:true` count).
- **Interaksi sizing×slot: NOL** — sizing (computeDeployAmount) tak tahu slot; enforcement (count) tak
  pengaruhi sizing. Itu sumbar masalah: sizing gak bagi modal ke slot → maksimalisasi 2 posisi tak terjamin.

### 4. bins_below — config tetap atau computed?
- **COMPUTED** (bukan key tetap). Formula linear (prompt.js:153, index.js:1009, computeBinsBelow index.js:1457):
  `bins_below = round(minBinsBelow + (volatility/5)×(maxBinsBelow − minBinsBelow))` clamp `[minBinsBelow, maxBinsBelow]`.
- **Cara nyempitin ~×0.75 yg BENER:** turunkan **`maxBinsBelow`** (& `defaultBinsBelow`); `minBinsBelow` sudah
  di **floor keras 35** (`MIN_SAFE_BINS_BELOW`, config.js:34/46+579) → tak bisa turun. v2: min35/max69/def69
  (mode aktual = 69 = ceiling). ×0.75: **max 69→52, def 69→52, min 35 tetap**. (Backtest A: ×0.75 → OOR-bawah ~2%.)

### 5. rent — nilai & sumber
- **`POSITION_RENT_ESTIMATE_SOL = 0.057`** (tools/dlmm.js:1892, "Empirical rent of a Meteora positionV2 account").
- `getPositionsRentSol()` (dlmm.js:1895+) baca on-chain real, **fallback 0.057** kalau gagal. R-output ≈0.0574 cocok.
